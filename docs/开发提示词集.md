# 学业预警帮扶平台 · 开发提示词集

> 版本：v1.0 ｜ 代码基线：v1.2.0（本项目根目录）
> 用途：把「双端权限边界 + 创新功能」的规划落成一套**可直接复制给 AI 编码助手**的开发提示词。
> 配套文档：`docs/任务流设计.md`（任务流设计）、`README.md`（实现说明）、`../项目技术方案与制作过程（PPT素材包）.md`（答辩素材）

---

## 〇、怎么用这套提示词

1. **一个提示词 = 一次会话 = 一个可独立验收的提交。** 不要一次性把多个提示词丢给 AI，会互相污染。
2. **每次新开会话，先贴第 1 节的「通用上下文块」，再贴一个任务提示词。** 提示词之间不共享上下文，所以每个提示词都写成自包含的。
3. **严格按依赖顺序做**（见第 2 节依赖图）。`PROMPT-00` 是所有后续任务的地基，必须先做。
4. **每个提示词完成后，跑一遍附录 A 的回归清单**，并让 AI 更新 `README.md` 对应章节（通用上下文块里已约定）。
5. 提示词里的**验收标准是硬门槛**。AI 说"已完成"不算完成，要能逐条复现。

### 当前基线的一个关键事实

现在的「双端区分」**只做到了 UI 层**：

| 现状 | 位置 | 结论 |
|---|---|---|
| 两端导航分开 | `index.html:31-35` / `student.html:12-16` | ✅ 已分离 |
| 页面级路由守卫 | `session.js:129-140` `guard()` | ✅ 已分离 |
| 学生端「困难申报」 | `student.js:135-137` | ❌ **是假的**：只弹 toast 和假工单号，不写 localStorage |
| 教师端处理申报 | `app.js` 全文 | ❌ 不存在任何 `appeal` / `申报` 逻辑 |
| 数据层权限 | 无 | ❌ 学生端可读写教师端 localStorage 键 |

所以这套提示词的主线是：**把"菜单不同"升级为"数据可见性与操作权限不同"，并且守卫要落在数据层而不只是 UI 层。**

## 一、通用上下文块（每个会话开头必贴）

````text
【项目背景】
我在开发「学业预警帮扶平台」，一个 Electron 桌面端双角色应用：
- 教师端 index.html + app.js：学情预警、班级管理、知识库、任务流、系统设置
- 学生端 student.html + student.js：学业画像、学习计划、错题本、消息通知、困难申报
- 登录页 login.html + login.js：身份选择

【技术栈与硬约束】（必须严格遵守，违反视为任务失败）
1. 纯原生 HTML/CSS/JavaScript，**无构建步骤、无 npm 依赖**。禁止引入任何第三方库，禁止使用 webpack/vite/babel。
2. 代码风格是 **ES5 风格**：用 `var`，不用 `let/const`；不用箭头函数；不用模板字符串；不用解构、展开、可选链。
   请先读 app.js / student.js / session.js 模仿现有风格，保持完全一致。
3. 持久化只用 `localStorage`（分键存储）。没有后端、没有数据库。
4. **禁止使用 `eval` / `new Function`**（flowEngine.js 已刻意用自研表达式求值器规避）。
5. 所有新增 UI 必须复用 style.css 的既有类和 CSS 变量

   `--radius` / `--shadow-card`、`.card` / `.btn` / `.btn-primary` / `.btn-secondary` / `.btn-sm` /
   `.tab-item` / `.tab-panel` / `.form-group`），不要写新的硬编码色值。
6. 必须离线可用：任何 AI 调用失败的路径都要有降级分支，不能白屏或卡死。
7. 中文文案，注释用中文，注释要解释「为什么」而不是复述代码。

【关键模块，动手前请先读】

- multimodal.js   多模态能力层（OCR/ASR/答疑/文档解析/错题本 MM.wrongBook/回流预警）
- flowEngine.js   轻量任务流引擎（JSON DSL，7 种节点，运行记录存 localStorage:flowRuns）
- flows.js        3 条内置任务流定义
- riskPlugins/    可插拔风险评分规则（pluginManager.js 的 RiskPluginManager.score/getActive/setActive）

【已存在的 localStorage 键】【禁止随意改名，新键必须在此登记】
- appSession.v1           当前会话
- authLog                 身份切换/登录登出日志（保留 50 条）
````

## 三、任务提示词

### PROMPT-00 · 数据层与字段级权限底座

> **依赖**：无（前置，必做）
> **涉及文件**：新增 `permissions.js`；改 `index.html` / `student.html` / `login.html`（脚本加载顺序）
> **预估**：半天

````text
【任务】为双端应用建立「字段级权限」底座，把现在只存在于 UI 层的角色区分下沉到数据层。

【现状与问题】
1. session.js 的 Session.guard(expectedRole) 只做页面级守卫：身份不符就跳回登录页。
2. 但教师端与学生端运行在同一个 Electron 会话里，共享同一个 localStorage。
   结果：只要学生在学生端页面打开开发者工具，就能直接读写教师端的键
   （studentWarningStates / studentWarningHistory / agentConfigs 等）。
   也就是说现在的"双端区分"在数据层是完全不设防的。
3. 没有任何"谁访问了谁的数据"的记录能力。

【任务目标】新建 permissions.js，提供四点能力：

(1) 字段级可见性矩阵
    定义每个角色能读/写哪些字段。至少覆盖：
    - teacher：可读全部学生字段、可写 riskLevel/status/ticket*/supportPlan
    - student：仅可读自己的 name/className/grades/homework/attendance/riskLevel/status，
      仅可写自己的申报与申诉（不可写 riskLevel/status）
    支持"本人 vs 他人"两种粒度：老师看全班，学生只看自己那一条。

(2) 统一 API
    Perm.ROLE 常量
    Perm.fields(role, isSelf)              -> { read: [...], write: [...] }
    Perm.can(role, action, isSelf)         -> boolean   // action 如 'warning:adjust' 'appeal:review'
    Perm.filter(role, record, isSelf)      -> 去掉无权字段后的新对象（不修改入参）
    Perm.guardData(role, targetStudentId)  -> 学生访问非本人数据时抛错/提示并拒绝
    Perm.audit(entry)                      -> 写入数据访问审计日志

(3) 数据访问审计
    写 localStorage 新键 dataAccessLog，数组，最多保留 500 条，新的在前。
    条目结构：
    { at: ISO时间, actorRole, actorId, actorName, subjectId, subjectName,
      action: 'view'|'export'|'write', fields: [字段名], page: 页面文件名 }
    audit 内部必须 try/catch，写失败不能影响主流程。
    注意：读操作要节流去重，避免同一页面同一对象刷屏——
    同一 actorRole+actorId+subjectId+action 在 5 秒内只记一条。

(4) 会话联动
    Perm 未登录时（Session.current() 返回 null）一律拒绝并返回 false。

【实施要求】
- permissions.js 用 IIFE + 'use strict' 包裹，挂到 window.Perm，并 `if (typeof module !== 'undefined' && module.exports) module.exports = Perm;`
- 用 ES5 风格，模仿 session.js 的写法（参考它的 read/write/try-catch 防御风格）。
- **加载顺序**：必须排在 session.js 之后、其他业务脚本之前。
  修改 index.html、student.html、login.html 三处的 <script> 顺序，并同步更新 README.md 里的"脚本加载顺序"说明。
- 兼容老数据：老 localStorage 里没有的字段，filter 时按"缺失即跳过"处理，不要抛错。

【验收标准】（逐条手工验证，并在回复里说明如何复现）
1. 控制台执行 Perm.fields('student', false) 只返回只读的少量字段，且不含 riskScore。
2. 控制台执行 Perm.filter('student', {name:'张三', grades:'高数 85', riskScore:92, supportPlan:{...}}, false)
   结果中不含 riskScore 和 supportPlan，且原对象未被修改。
3. 学生角色调用 Perm.guardData('student', '其他学号') 返回拒绝。
4. 触发一次学生端查看自己的画像后，localStorage.dataAccessLog 出现一条 action:'view' 的记录，
   且 5 秒内重复查看不新增第二条。
5. 清空 localStorage 后应用仍能正常启动（老数据兼容）。
6. login.html / index.html / student.html 三个页面均无控制台报错。

【约束】
- 不要在这一步改造任何业务页面逻辑，只做底座 + 在三处 HTML 挂上脚本。业务接入交给后续提示词。
- 不要引入任何依赖。
````

### PROMPT-01 · 困难申报改造为真实工单（含修复假表单）

> **依赖**：PROMPT-00
> **涉及文件**：`student.js`（renderAppeal，135-137 行）、`app.js`（教师端新增处理视图）、`index.html`（新增 Tab）
> **预估**：半天 ｜ **优先级：最高（先修缺陷，再谈创新）**

````text
【任务】把学生端「困难申报」从假表单改成真实工单，并在教师端建立接单处理闭环。

【现状：这是一个真实缺陷，必须先修】
student.js 第 135-137 行的 renderAppeal() 存在两个问题：
1. 整个表单是纯前端表演：提交按钮只做
   `document.getElementById('appealResult').style.display=''; showToast('申报已提交');`
   根本没有读取输入框的值，也没有写 localStorage。工单编号 AP-xxxx 是当场现编的假号。
2. app.js 全文检索不到任何 appeal / 申报 / Appeal 相关逻辑。
   => 学生在页面上看到"已提交"，辅导员那边永远收不到。这是答辩时最容易被现场戳穿的点。

【任务目标】
一、学生端（student.js 的 renderAppeal）
1. 保留现有表单字段（申报类型 select / 详细描述 textarea / 联系方式 input），
   但提交时必须做真实校验：描述为空或少于 10 字时提示"请把困难描述得再具体一些"，不提交。
2. 写入 localStorage 新键 supportTickets，数组，新的在前，最多 200 条。
   条目结构：
   { id: 'ST-' + 时间戳36进制, studentId, studentName, className,
     type, urgency, desc, contact, createdAt: ISO,
     status: 'pending'|'accepted'|'closed',
     handler: '', handleLog: [], result: '' }
3. 提交成功后：
   - 显示真实工单号与"辅导员会在 48 小时内响应"的提示；
   - 清空表单；
   - 在页面下方渲染「我的申报记录」列表：类型 / 提交时间 / 状态徽章 / 处理结论。
4. urgency 由前端做一个**保守的本地关键词分级**（不要接大模型，先做确定性的）：
   描述中包含 自伤/自杀/轻生/不想活/结束生命 等词 → urgency='urgent'，
   并在提交成功后额外弹出一个醒目提示，给出校内心理援助热线占位文案与"请立即联系辅导员"。
   其余 → urgency='normal'。
   （注意：这只是初筛提示，不是诊断，文案不要做任何医学判断。）
5. 复用 Perm（PROMPT-00）：提交时校验 role==='student' 且 studentId 为本人；读取记录只读本人。
   同时调用 Perm.audit 记录 action:'write'。

二、教师端（app.js + index.html）
1. 在 index.html 的 tab-bar（277-285 行）新增一个 `<button class="tab-item" data-tab="tickets">学生申报</button>`，
   并在 contentDetail 内新增对应的 `<div class="tab-panel" id="tabTickets">`。
2. 在 app.js 的 switchTab() 里按**现有那串 if 的写法**（参考 'checkin' / 'kbadmin' 分支）
   加上 'tickets' 分支，保证其他面板的 display 都被正确关掉。不要重构 switchTab。
3. 渲染申报列表：按 urgency（urgent 优先）+ 时间倒序。每行显示
   学生姓名/学号/班级/类型/紧急标记/提交时间/状态，点击可展开描述与联系方式。
4. 操作按钮：
   - 「接单」→ status='accepted'，写入 handler=当前登录教师姓名，handleLog 追加一条
   - 「填写处理结论」→ 弹输入框，写入 result，status='closed'，handleLog 追加
   - 每次状态变更都要写 authLog（复用 Session.log）与 Perm.audit，形成留痕
5. 顶部显示统计：待处理 / 处理中 / 已结案 三个数字。
6. 数据实时性：监听 window 的 'storage' 事件（参考 multimodal.js 回流预警已有做法），
   学生端提交后教师端列表自动刷新。

【验收标准】
1. 学生端填一段 20 字描述提交 → 学生端立即出现记录行；
   localStorage.supportTickets 里有该条目，字段完整、id 唯一。
2. 描述只有 3 个字时提交被拦截，不产生数据。
3. 描述包含"轻生"时 urgency='urgent'，并出现紧急提示文案。
4. 切换身份登录教师端 → 「学生申报」Tab 能看到刚提交的工单，urgent 排在最前。
5. 点「接单」→ 状态变处理中、handler 是教师名；填结论 → 状态变已结案、结论回显。
6. 学生端刷新后能看到状态和结论已更新。
7. 后端数据（localStorage）键名、字段与本文档完全一致。

【约束】
- 不要接大模型做意图识别（那是 PROMPT-07 之后的事），这一步必须是确定性逻辑，保证演示不依赖网络。
- 不要改动 studentWarningStates 的结构。
- 顺带修复 app.js 第 1740 行的既有 bug：
  `function addToHistory(result) { var items = []; try { items = raw ? JSON.parse(raw) : []; } ... }`
  这里的 `raw` 未定义（应为 `localStorage.getItem('studentWarningHistory')`），会抛 ReferenceError。
  修好后在回复里单独说明。
````

### PROMPT-02 · 预警解释卡（可解释性）

> **依赖**：PROMPT-00
> **涉及文件**：`app.js`（风险分析处新增快照写入）、`student.js`（画像/通知页渲染解释卡）
> **预估**：1 天

````text
【任务】让每一条预警都能回答"凭什么是我"，并且把「当时的判定依据」固化存下来。

【为什么要快照，而不是实时算】
现在风险等级由 RiskPluginManager.score() 实时计算，而规则可以被教师随时切换
（riskPluginActive: basic / weighted / strict，见 riskPlugins/pluginManager.js）。
如果学生申诉时系统用"现在的规则"重算，得到的可能是和当初完全不同的结论——
申诉就变成了对着一个移动的靶子。所以必须在**生成预警的那一刻**把依据快照存下来。

【任务目标】
一、新增 localStorage 键 warningSnapshots
   { [学号]: { at: ISO, pluginId, pluginName, riskLevel, riskScore,
               factors: [ { dim, label, rawValue, weight, contribution, hit: true|false } ],
               evidenceRefs: [ { type, ref, label } ] } }
   - dim 维度建议：'grade'（成绩）/ 'attendance'（出勤）/ 'homework'（作业）/ 'experiment'（实验）/ 'wrongbook'（错题回流）
   - contribution 是该维度对总分的实际贡献，factors 各项 contribution 之和应能解释 riskScore
   - evidenceRefs 先留空数组，由 PROMPT-04 填充
   - 最多保留 200 条（按 at 倒序裁剪）

二、写入时机
   在 app.js 里生成预警 / 风险等级发生变化的地方写入快照。
   动手前请先用 grep 找到实际调用 RiskPluginManager.score 的位置，
   以及保存 studentWarningStates 的地方（约 app.js:750-765 的 saveStudentStates），
   把快照写入接在那条链路上，确保"状态变了快照一定同步更新"。

三、学生端展示（student.js）
   在「学业画像」页顶部（或学生能看到自己预警详情的地方）渲染「预警解释卡」：
   1. 结论区：风险等级徽章 + 安全分（复用 index.html 的 risk-badge / risk-ring 视觉语言）
   2. 依据区：把 factors 渲染成横向贡献条（维度名 + 该维度数值 + 贡献分占比），
      命中的维度用 --color-danger，未命中用 --color-text-muted。
   3. 规则区：一行小字"本次判定使用规则：{pluginName}（{pluginId}）"，并注明快照时间。
   4. 一句话自然语言解释，**用规则拼装，不要调大模型**（保证离线可复现）：
      例如"你在「成绩」维度未达阈值（高数 58 分），该项贡献 30 分，是本次预警的主要原因。"
      模板：命中维度中 contribution 最高的那一项作为"主要原因"，其余命中项列为"次要因素"。
   5. 底部占位一个「我要申诉」按钮（本提示词只做按钮与提示，
````

### PROMPT-03 · 双向申诉闭环

> **依赖**：PROMPT-02（需要快照）
> **涉及文件**：`student.js`、`app.js`、`index.html`
> **预估**：1.5 天 ｜ **答辩核心亮点**

````text
【任务】打通「学生申诉 → 教师复核 → 结论回写学生」的双向闭环。

【背景】
现在系统是单向的：教师端判断，学生端接收。学生没有任何质疑渠道。
本任务要把它变成可辩驳的——这是"算法可解释性"在教育场景最直接的落地。

【任务目标】
一、学生端（student.js）
1. 在 PROMPT-02 的解释卡上把「我要申诉」按钮做成真功能：
   点击 → 弹出申诉表单：申诉理由（必填，≥10 字）+ 申诉类型
   （选项：数据有误 / 情况特殊 / 已改善请复核 / 其他）。
   表单里只读展示触发申诉的那份快照摘要（规则名 / 等级 / 主要因素 / 快照时间），
   让学生清楚自己在质疑什么。
2. 写入 localStorage 新键 warningAppeals，数组，新的在前，最多 200 条：
   { id: 'AP-' + 时间戳36进制, studentId, studentName, className,
     warningAt, snapshot: {…第02步的快照摘要…},
     type, reason, createdAt: ISO,
     status: 'pending'|'accepted'|'rejected',
     reviewer: '', reviewedAt: '', conclusion: '' }
3. 幂等：同一学生 + 同一 warningAt 若已有 pending 申诉，拒绝重复提交并提示"你已提交过申诉，正在处理中"。
4. 「消息通知」页新增一类消息"预警复核结果"：
   展示结论（采纳/驳回）+ 复核人 + 结论说明 + 时间；未读的加红点（可复用现有 badge 样式）。

二、教师端（app.js + index.html）
1. 在已有的「操作记录」Tab（index.html:279，tabHistory）里新增一个
   「申诉复核」区块（不要新建 Tab，直接扩展这个页，保持信息架构稳定）。
2. 列表按 pending 优先 + 时间倒序，展示：学生姓名/学号/班级/预警时间/申诉类型/理由摘要。
   点击展开可看到该生**当时的规则快照**（这是复核的关键依据）。
3. 操作：
   - 「采纳申诉」→ 弹出结论文本框（必填）→ status='accepted'，
     同时把 studentWarningStates[学号].status 置为 'reviewing'（核查中），
     并把 riskLevel 降一级（高→中、中→低、低不变），写入 studentWarningHistory 留痕。
   - 「驳回申诉」→ 结论文本框（必填）→ status='rejected'，预警状态保持不变。
   - 两个操作都要：reviewer=当前教师名、reviewedAt、写 authLog（复用 Session.log）、写 Perm.audit。
4. 顶部显示待复核数量徽章。

三、权限与安全
- 学生端仅能读写本人申诉；教师端可读全部。
- 教师端处理时校验 Perm.can('teacher','appeal:review')。
- 所有写操作走统一函数，禁止在 UI 事件里直接裸写 localStorage。

【验收标准】
1. 学生在解释卡点申诉，填 15 字理由提交 → warningAppeals 出现 pending 条目，含快照摘要。
2. 重复提交同一 warningAt → 被幂等拦截，localStorage 不新增条目。
3. 教师端「操作记录」页看到该申诉，能展开看到当时的规则快照。
4. 点「采纳申诉」填结论 → 申诉状态 accepted；该生 riskLevel 降一级；
   studentWarningHistory 新增一条记录；authLog 与 dataAccessLog 均有留痕。
5. 学生端刷新 → 「消息通知」出现复核结果，显示采纳 + 复核人 + 结论。
6. 点「驳回申诉」→ 状态 rejected，风险等级不变。
7. 断网状态下全流程可跑通（本任务不涉及任何网络调用）。

【约束】
- 不要引入工单状态机的新状态值，复用 students.js 里既有的
  STATUS_LABEL：pending/supporting/reviewing/resolved。
- 不要改动 studentWarningStates 已有字段的含义。
- 降级规则必须是"降一级"这一确定性逻辑，不要用大模型决定采纳与否——
  最终决策权在人，AI 不参与裁决。
````

### PROMPT-04 · 证据链下钻

> **预估**：1 天

````text
【任务】让每条预警都能下钻到原始多模态证据，形成可追溯的证据链。

【为什么这是亮点】
答辩时评委最常问"你说 AI 判断他有风险，依据呢？"
能当场点开：那张成绩单照片、OCR 识别原文、错题照片、以及这次判断经过的任务流时间线——
这一下就把"黑盒打分"变成了"可审计的决策"。

【任务目标】
一、填充 PROMPT-02 快照里的 evidenceRefs 数组
   每条预警快照在写入时，尽最大可能收集关联证据引用：
   { type, ref, label, at }
   type 取值与来源：
   - 'wrongbook'  → ref 为 wrongBook 里的错题 id，label 如"错题：高等数学·极限（未掌握）"
   - 'ocr'        → ref 为 OCR 结果文本的 hash 或时间戳，label 如"成绩单 OCR 识别原文"
   - 'asr'        → ref 为语音转写记录标识，label 如"语音申报转写"

   - 'ticket'     → ref 为 supportTickets 的工单号
   动手前先读 multimodal.js 里 MM.wrongBook.list() 的返回结构和 flowEngine.js 里
   flowRuns 的存储结构，按真实字段来，不要臆造。找不到对应证据就留空数组，不要造数据。

二、教师端：学生详情页新增「证据链」入口
   在 tabDetail（学生详情）里加一个「证据链」折叠区或按钮，点开后在弹层/抽屉中展示：

   2. 点击可查看详情：
      - 错题 → 展示题目、知识点、复习次数、状态（从 MM.wrongBook 读）
      - OCR → 展示识别原文与当时使用的引擎（tesseract / vlm / mock）与置信度
      - 任务流 → 展示该次运行的完整时间线（节点名 / 状态 / 耗时 / 输出摘要 / 错误），
        直接复用任务流页面已有的时间线渲染逻辑，不要重写一份
   3. 顶部一句话："该学生的风险结论由以下 N 条证据支撑"。
   4. 若 evidenceRefs 为空，明确显示"暂无关联证据（该预警由规则引擎直接命中）"，不要留白。

三、学生端：同一份证据，不同粒度
   学生端也能看到与自己相关的证据，但**只展示本人原始数据**，
   不展示教师端的内部研判过程（如帮扶方案草稿、其他同学对比数据）。
   这一"同一份证据、两端不同呈现粒度"的设计本身就是双端区分的体现，请在 README 里说明。

四、权限

五、健壮性
   - 证据引用指向的数据可能已被清理（错题本只留 200 条、flowRuns 只留 50 条）。

【验收标准】
1. 学生上传 3 道同知识点错题触发回流预警后，教师端该生证据链能看到 3 条错题证据。
2. 点击任务流证据 → 能看到节点时间线，与「任务流」页面看到的内容一致。

5. 学生端登录后只能看到自己的证据，构造他人 id 调用被拒绝。
6. dataAccessLog 有对应的查看留痕。

【约束】
- 不要新建证据存储，证据一律**引用**已有模块的数据，避免数据双写不一致。
- 不要重写任务流时间线渲染，复用现有实现。
````

### PROMPT-05 · 数据访问审计 + 学生端隐私中心

````text
8. 审计日志里不出现任何字段的实际值（手工检查一条记录）。

【约束】
````

### PROMPT-07 · 案例库反哺（给三 Agent 加记忆）

> **依赖**：PROMPT-03（需要已结案的申诉/工单数据）
> **涉及文件**：`app.js`（工单状态机）、`flows.js`（预警帮扶闭环流）、`flowEngine.js`
> **预估**：2 天 ｜ **"系统会越用越准"的唯一证据**

````text
【任务】把已结案的帮扶工单沉淀成案例库，在新预警生成帮扶方案时检索相似案例反哺 Agent2。

【现状】
三条任务流（flows.js）里的 Agent1 预警分析师 / Agent2 帮扶规划师 / Agent3 执行监督员
是**完全无状态**的：每次调用都从零开始生成方案，历史上哪种方案真的有效，
系统完全不知道。已有的 localStorage:flowRuns 记录了每次运行的节点级时间线，但没被利用。

【任务目标】
一、案例沉淀
   新增 localStorage 键 caseBase，数组，新的在前，最多 300 条：
   { id: 'CASE-' + 时间戳36进制,
     ticketId, studentId, className,
     riskLevel, riskScore,
     factors: [ {dim, label, contribution} ],        // 取自 warningSnapshots
     planName, planSummary,                            // 采用的帮扶方案（Agent2 产出摘要）
     checkinRate,                                      // 执行期打卡完成度 0-1
     outcome: 'resolved'|'escalated',                  // 最终结果
     durationDays,                                     // 从生成工单到结案/升级的天数
     closedAt: ISO }
   触发时机：工单状态变为 resolved（已解除）或 escalated（已升级）时自动沉淀。
   结案时若缺少 factors，从 warningSnapshots 补读；仍缺失则存空数组，不要造数据。

二、相似度检索（先用现有能力，不要上向量库）
   实现 findSimilarCases(snapshot, k)：
   1. 特征向量化：把 factors 归一化成 {dim: contribution占比}，
      再拼接 riskLevel（高/中/低 映射为 0/0.5/1）。
   2. 相似度 = 各维度贡献占比的曼哈顿距离取反 + riskLevel 相同加成。
      参考项目已有的轻量检索思路（multimodal.js 的 matchKnowledge 用标签命中 + 字符bigram重叠），
      保持零依赖、确定性、可解释。
   3. 返回 Top-k（默认 3），并给出每条案例的相似度分数与**可读的相似理由**
      （如"风险等级相同，且都以「成绩」为主要因素"）。
   4. 案例数不足 3 条时返回全部并在 UI 上说明"案例库样本较少，仅供参考"。

三、反哺 Agent2
   修改 flows.js 的「预警帮扶闭环流」定义：在调用 Agent2（帮扶规划师）之前，
   插入一个 `tool` 节点 `case.retrieve`，把检索结果作为上下文注入 Agent2 的输入。
   参考历史案例的措辞要克制，例如：
     "参考历史案例：3 例相似画像的学生中，采用「每周 2 次一对一辅导 + 错题专项」的
      2 例在 21 天内解除预警；采用「仅推送学习资料」的 1 例最终升级为二级预警。"
   **关键**：Agent2 的产出仍然只是建议，人工审批节点不变。AI 不得自动决策。

四、教师端展示
   1. 在「帮扶方案」Tab 生成方案时，显示「相似历史案例」区块：
      每条含相似度、风险画像摘要、当时方案、打卡完成度、最终结果、耗时。
   2. 在「班级概览」新增「有效干预方式」统计：
      按方案类型汇总解除率（解除数 / 总数），样本数 < 3 的标注"样本不足"。
      这一块直接回应"哪种干预真正有效"，是答辩的加分素材。
   3. 反哺统计：显示"本次方案参考了 N 条历史案例"。

五、健壮性与隐私
   - 案例库里的学生信息要**脱敏**：只保留班级与风险画像，不展示姓名学号给 Agent。
     （教师端 UI 可按权限显示姓名，但注入模型的上下文中必须匿名化。）
   - 单条案例字段缺失（老数据）时跳过该案例，不要让整个检索失败。
   - 检索为空时流程照常走，Agent2 退化为无案例上下文的原始行为，并在 UI 标注"无历史案例可参考"。

【验收标准】
1. 把某工单走完流程至「已解除」→ caseBase 新增一条，outcome='resolved'，factors 非空。
2. 走完一条至「已升级」→ 新增 outcome='escalated' 的案例。
3. 对同一学生重新生成预警 → 帮扶方案页显示相似案例列表，含相似度与相似理由。
4. caseBase 为空时，流程仍能跑通，UI 显示"无历史案例可参考"，无报错。
5. 「有效干预方式」统计的解除率计算正确（手工按 caseBase 数一遍核对）。
6. 检查注入 Agent2 的上下文文本，确认其中不含任何学生姓名与学号。
7. `node test-risk.js` 仍全绿。

【约束】
- 不要引入向量库或 embedding 服务，先用确定性相似度；README 里把"接 sqlite-vec"列为后续演进。
- 不要改动 Agent1 / Agent3 的系统提示词与温度配置（temperature 0.3 / 0.7 / 0.1 是刻意设计）。
- 不要新增 AI 决策点，人在环中的原则不能破。
````

### PROMPT-08 · 正向预警 / 育优预警

> **依赖**：PROMPT-00
> **涉及文件**：`app.js`、`student.js`、`riskPlugins/`
> **预估**：1 天

````text
【任务】增加一套正向评分，把系统从"只盯风险"扩展为"预警 + 育优"。

【为什么做】
现在的系统只会说"你有危险"。加一套反向打分，说"你在这方面很强，建议试试竞赛/保研/项目"，
叙事立刻从"盯差生"变成"学生发展平台"。而且用的还是同一批字段，边际成本极低。

【任务目标】
一、正向评分（新增，不改动原有风险评分）
   新建 riskPlugins/positiveRule.js，与现有三套风险插件**并列但独立**，
   不要插进 RiskPluginManager 的 plugins（那会影响风险评分）。
   建议单独一个 PositiveRuleManager，或直接用独立模块 + 一个 apply 函数。
   评分维度（每项 0-100，加权求和）：
   - 学业表现：加权均分（复用 weighted 插件的课程权重思路：高数/编程 1.2，其余 1.0）
   - 学习韧性：错题本复习次数、复习打卡连续性（从 MM.wrongBook.list() 统计）
   - 行为自律：出勤率、作业提交率
   - 进步幅度：与历史记录（studentWarningHistory）相比的分数提升
   输出：{ score, level: 'A'|'B'|'C', strengths: [ {dim, label, score, reason} ] }
   strengths 要给出可读理由，例如"出勤全勤且作业零缺交，自律性突出"。

二、学生端
   在「学业画像」页新增「我的优势」卡片：
   1. 优势标签（取 strengths 中分数最高的 2 项），用 --color-success 系配色。
   2. 每条优势一句话理由。
   3. 建议区（**规则映射，不调大模型**）：
      - 学业表现 A → "可尝试学科竞赛 / 参与科研项目"
      - 学习韧性 A → "你的错题复习习惯很好，可以带同学一起复习"
      - 进步幅度 A → "本学期进步明显，可申请进步奖学金（具体以学校政策为准）"
      每条建议后缀"具体以学校政策为准"，不要给绝对承诺。
   4. 若学生同时有风险预警，先显示预警解释卡，再显示优势卡片——
      文案上要正向，避免打击。这一点请在实现时用一句注释说明理由。

三、教师端
   在「班级概览」新增「可重点培养名单」表格：
   学生 / 班级 / 优势得分 / 优势标签 / 风险等级（若有）
   支持按优势得分排序，支持导出一份「育优名单」（复用现有导出能力）。
   注意：这份名单同时显示风险等级，方便辅导员看到"高风险但某维度有潜力"的学生——
   这类学生最容易在帮扶中被忽略，是这套设计真正的价值点。

四、文案红线（重要）
   - 正向评分**不得**成为任何奖励的自动依据，UI 上必须写明"仅供辅导员参考"。
   - 不展示学生之间的排名，只展示个人优势（避免制造新的攀比与焦虑）。
   - 涉及奖学金/保研的表述一律加"以学校政策为准"。

【验收标准】
1. 全勤、成绩优秀的学生 → 优势等级 A，strengths 至少 2 项且理由是具体数据支撑的。
2. 高风险学生若某项突出（如错题复习次数高）→ 仍能看到该项优势标签。
3. 「可重点培养名单」可按优势得分排序，导出文件内容与页面一致。
4. 断网可完整使用（本任务不调用任何模型）。
5. 原有风险评分与 test-risk.js 6 条用例不受影响（全绿）。
6. 页面上不存在学生间的排名展示。

【约束】
- 绝不修改现有风险评分逻辑，正向与负向两套评分必须彼此独立。
- 不接大模型，全部规则化，保证可解释、可复现。
- 不新增 localStorage 键（正向评分实时计算即可），若确需缓存请在 README 登记。
````
