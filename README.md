# 学业预警帮扶平台

面向高校学业预警与帮扶工作的 Electron 桌面平台，提供教师工作台、学生自助端、可视化任务流和三 Agent 协同。教师可查看风险证据、跟进帮扶工单、复核执行情况；学生可查看学业画像、学习计划并维护错题本。平台采用本地存储，演示数据可一键载入。

项目亮点：确定性规则负责风险评分，三 Agent 分别承担预警解释、帮扶规划和执行复核；模型结果须通过结构与证据校验，失败时转人工处理。任务流支持条件分支、人工审批、运行留痕及多模态录入。

## 交付须知（两件必须先处理的事）

### 1. `node_modules` 是 junction，**不要直接压缩整个文件夹**

```
node_modules  →  链接到本项目源码目录之外（目录联接，非真实目录），因此不随仓库提交
```

直接打包会把联接原样带上，评审解压后 `npm start` 会因为找不到 `electron` 而失败。正确做法：

```powershell
# 打包前排除 node_modules（评审端自己 npm install）
tar -a -c -f 学情预警-交付.zip --exclude=node_modules 学情预警
# 或把源码复制到干净目录后再压缩
```

`package.json` 与 `package-lock.json` 是完整一致的（lockfileVersion 3，含 371 个包），
评审端 `npm install` 可复现同一套依赖。

### 2. 凭据只放在本地覆盖文件

`config.js` 只包含无害占位符且默认使用 Mock。真实凭据只能写入已忽略、打包时也明确排除的
`config.local.js`（参考 `config.example.js`），不要将真实密钥提交到仓库或放入安装包。若凭据被公开，应在对应供应商控制台撤销或轮换。

## 双端权限与数据访问审计

页面级守卫（`Session.guard`）只能拦"打开哪个页面"，拦不住"在学生端页面打开控制台直接读写教师端的键"。
`permissions.js` 把角色区分下沉到数据层：

```js
Perm.ROLE                                   // { TEACHER:'teacher', STUDENT:'student' }
Perm.fields(role, isSelf)                   // -> { read:[字段名], write:[字段名], effectiveRead:[] }
Perm.can(role, 'warning:adjust', isSelf)     // -> boolean（未登录一律 false）
Perm.filter(role, record, isSelf)           // -> 裁剪后的新对象（不改入参，缺字段即跳过）
Perm.filterSnapshot(role, snap, isSelf)     // -> 裁剪「判定依据快照」字段域（见下节）
Perm.guardData(role, targetStudentId)       // -> { ok, isSelf, error? }，学生越权时拒绝
Perm.audit({ action, subjectId, fields })   // -> 写数据访问审计（5 秒内同源去重）
Perm.myLog()                                // -> 仅当前学生本人的访问记录
```

| 角色 | 可读 | 可写 |
|---|---|---|
| 教师 | 全部学生字段（含 `riskScore` / `supportPlan` / `ticket*` / `operationLog`） | 研判与治理字段（`riskLevel` / `status` / `ticket*` / `supportPlan`）及名单更正 |
| 学生 | 仅本人 `name` / `className` / `grades` / `homework` / `attendance` / `riskLevel` / `status` | 仅本人的申报与申诉（写入独立存储键，不碰 `studentWarningStates`） |

**加载顺序**（三个页面一致，必须排在所有业务脚本之前）：

```
session.js  →  permissions.js  →  students.js / onboarding.js / multimodal.js / flowEngine.js / app.js(或 student.js)
```

**审计日志**：新键 `localStorage.dataAccessLog`，最多 500 条、新的在前；每条只记录字段**名**不记录值，
结构为 `{ at, actorRole, actorId, actorName, subjectId, subjectName, action:'view'|'export'|'write', fields, page }`。
写入失败（如配额满）不会影响主流程。

> 说明：`Perm` 提供底座，业务侧接入见下方「写侧接入点」与学生端隐私中心。

### 业务侧接入点（写侧）

| 场景 | 动作 | 位置 |
|---|---|---|
| 教师查看某学生详情 | `view` | `selectStudent()`，fields 为 `name/className/grades/homework/attendance/riskLevel/status` |
| 教师导出学生报表 / 工单 / 打卡 / 台账 / 预警报告 | `export` | 导出下拉三项 + `exportLedger()` + `handleExport()` |
| 教师「应用并重算」评分规则 | `write` | `applyRule()` 逐生记 `riskLevel/riskScore` |
| 教师变更工单状态 | `write` | `changeStudentStatus()` 记 `status` |
| 教师处理申报 / 复核申诉 | `write` | `ticketAccept` / `ticketClose` / `reviewAppeal` |
| 学生查看自己的画像 | `view` | `renderProfile()`（actor 与 subject 都是本人） |
| 学生阅读预警解释卡 / 导出自己的数据 | `view` / `export` | `renderExplainCard()` / 隐私中心 |

同页面 5 秒内重复访问同一对象只记一条（节流）；只记字段**名**，不记字段值。

### 学生端「隐私中心」

学生端第五个 Tab，回答"谁在什么时候看过我的什么数据"：

- **谁看过我的数据**：按访问者聚合（「辅导员 张老师 访问过 12 次，最近 …」）+ 逐条明细
  （时间 / 访问者角色与姓名 / 动作：查看·导出·修改 / 涉及字段名 / 来源页面）。
  只读 `subjectId` 为本人 的记录（`Perm.myLog()`），越权由 `Perm.guardData` 拒绝。
- **我的数据**：成绩与出勤、错题本 N 条、申报 N 条、申诉 N 条；「导出我的数据（JSON）」
  复用 `preload.js` 的 `exportToFile`（不新增 IPC 通道），内容含本人的快照/错题/申报/申诉/访问记录。
- **数据说明**（大白话，不用"监控/审计"字眼）：哪些数据进评分、**心理类申报不进评分模型**、
  数据默认只存本机、本页记录仅本人可见。
- **申请更正数据**：填说明 → 写 `authLog` 留痕（不做真实流程，避免误导学生会自动改数）。

### 教师端「数据访问自查」

「系统设置」里显示本月**教师侧**的访问次数汇总（查看 / 导出 / 修改）。
刻意**不**展示"某学生打开过自己的隐私页"这类信息——那是反向监控，本项目不做。

## 学生困难申报（工单闭环）

学生端「困难申报」是一条**真实工单**链路（此前是假表单：只弹 toast、工单号当场现编、不落库）：

```
学生端提交（校验 + 紧急词初筛）
   ↓ 写入 localStorage:supportTickets
教师端「学生申报」Tab（紧急置顶 + 待处理/处理中/已结案统计）
   ↓ 接单（handler=教师名）→ 填写处理结论（status=closed）
学生端「我的申报记录」看到状态与结论
```

- 存储：`localStorage.supportTickets`，新的在前，最多 200 条。
  条目结构：`{ id:'ST-<时间戳36进制>', studentId, studentName, className, type, urgency, desc, contact, createdAt, status, handler, handleLog, result }`
- 校验：描述少于 10 个字直接拦截，不产生数据。
- 紧急分级（**确定性本地关键词，不接大模型**）：描述含「自伤 / 自杀 / 轻生 / 不想活 / 结束生命」等词 → `urgency='urgent'`，
  界面额外给出醒目求助提示（校内热线占位 + 全国心理援助热线 12356 + 请立即联系辅导员）。
  文案只做**初筛提醒**，不做任何医学判断。
- 权限：提交前走 `Perm.can('student','ticket:submit',true)`；教师处理走 `Perm.can('teacher','ticket:handle',false)`；
  两端均写 `Perm.audit` 与 `Session.log` 留痕。
- 实时性：教师端监听 `storage` 事件，学生提交后列表自动刷新。

## 预警解释卡与判定依据快照

每条预警都要能回答"凭什么是我"。学生端「学业画像」顶部的**预警解释卡**展示：
风险等级 + 安全分、各维度贡献条（命中项红色 / 未命中灰色）、本次使用的规则名与快照时间、
一句话自然语言解释（由规则拼装，不调用大模型），以及「我要申诉」入口。

**为什么要快照而不是实时重算**：评分规则（`riskPluginActive`）随时可被教师切换。
如果学生申诉时用"现在的规则"重算，得到的结论可能和当初完全不同，申诉就成了打移动靶。
所以判定依据必须在**生成预警的那一刻**固化下来。

- 存储：`localStorage.warningSnapshots`，按学号索引，最多 200 条（超出按 `at` 倒序裁剪）：

  ```
  { [学号]: { at, pluginId, pluginName, riskLevel, riskScore,
              factors: [ { dim, label, rawValue, weight, contribution, hit } ],
              evidenceRefs: [] } }
  ```

- `dim` 取值：`grade` / `attendance` / `homework` / `experiment` / `wrongbook` / `base`。
- 写入时机：只在**生成预警**时写（`handleResult` 链路）。切换规则只影响之后的判定，
  **不批量重写旧快照**——所以旧快照的 `pluginName` 会一直保留当时的规则。
- `evidenceRefs` 由后续的「证据链下钻」填充；本阶段恒为空数组。

**插件的 `detail(data)` 契约**（可选方法，不参与打分、不改变 `score()` 行为）：
返回 `{ score, factors[] }`，其中各项 `contribution` 之和必须等于 `score`，
且 `score` 必须与 `score(data).score` 完全一致。三套规则均已实现；
若某插件未实现 `detail`，学生端会退化为只展示总分并说明"该规则不提供分维度明细"。

**权限**：判定依据属于独立字段域，走 `Perm.filterSnapshot(role, snapshot, isSelf)` +
`Perm.audit({action:'view'})`；学生只能看到自己那一条，看不到他人快照。

## 双向申诉闭环

系统不再只是"教师判断、学生接收"——学生可以对判定提出质疑，形成可辩驳的闭环：

```
学生端「预警解释卡 → 我要申诉」（理由必填 ≥10 字 + 只读展示被质疑的快照摘要）
   ↓ 写入 localStorage:warningAppeals（同一快照已有 pending 时幂等拦截）
教师端「操作记录 → 申诉复核」区块（待复核置顶 + 顶部待复核计数）
   ↓ 「采纳申诉」结论必填 → 该生 riskLevel 降一级 + 工单状态置「核查中」+ 写 studentWarningHistory
   ↓ 「驳回申诉」结论必填 → 预警状态保持不变
学生端「消息通知 → 预警复核结果」（采纳/驳回 + 复核人 + 结论），未读带红点
```

- 存储：`localStorage.warningAppeals`，新的在前，最多 200 条：

  ```
  { id:'AP-<时间戳36进制>', studentId, studentName, className,
    warningAt, snapshot:{at,pluginId,pluginName,riskLevel,riskScore,mainLabel,mainRaw,factors[]},
    type, reason, createdAt, status:'pending'|'accepted'|'rejected',
    reviewer:'', reviewedAt:'', conclusion:'', noticeRead:false }
  ```

- 申诉里存的 `snapshot` 是**提交那一刻的快照摘要副本**，所以即使之后教师切换了评分规则，
  复核依据也不会漂移。
- 幂等：同一 `studentId + warningAt` 已有 `pending` 申诉时拒绝重复提交（"你已提交过申诉，正在处理中"）。
- 降级规则是确定性的"降一级"（高→中、中→低、低不变），**AI 不参与裁决**；采纳与否由人决定。
- 权限：学生只能读写本人申诉（`Perm.can('student','appeal:submit',true)`）；
  教师复核校验 `Perm.can('teacher','appeal:review',false)`；所有写入统一走 `Appeals.review()`，
  UI 事件里不直接碰 localStorage；两边都写 `Session.log` 与 `Perm.audit` 留痕。
- 通知的已读状态挂在申诉记录自身的 `noticeRead` 上，不新增存储键。

## 证据链下钻

预警解释卡回答"凭什么是我"，证据链回答"依据在哪"——评委追问时能当场点开原始材料。

**只引用、不双写**：证据一律引用已有模块的数据，不新建证据存储，避免多处写入不一致；
找不到对应证据就留空，不造数据。

| 证据类型 | 引用来源 | 详情展示 |
|---|---|---|
| `wrongbook` | `localStorage.wrongBook`（本人错题） | 科目/知识点/掌握状态/复习次数 + 题目原文 |
| `ocr` | 任务流运行记录里的 OCR 节点输出 | 识别原文 + 引擎 + 置信度 + 是否降级 |
| `asr` | 任务流运行记录里的转写节点输出 | 转写原文 |
| `flowrun` | `localStorage.flowRuns`（该生触发的运行） | 完整时间线（复用任务流页的渲染器，非重写） |
| `ticket` | `localStorage.supportTickets`（本人申报） | 类型/状态/紧急程度 + 描述与处理结论 |

- 引用结构：`{ type, ref, label, at }`，随预警一起写进 `warningSnapshots[学号].evidenceRefs`。
- 教师端：学生详情页出现「证据链 N 条 · 该学生的风险结论由以下 N 条证据支撑（错题本 2 条 · OCR 1 条 …）」，
  点「查看证据链」打开弹层，按类型分组、逐条可下钻。
- 学生端：同一份引用，但只展示**本人的原始材料**（`Evidence.forStudent` 过滤掉 `flowrun`），
  不暴露教师端的内部研判过程。
- 保留期：错题本留 200 条、`flowRuns` 留 50 条，引用失效时显示「该证据已过保留期」而不是报错；
  单条解析失败不影响其余证据。
- 权限：教师端查看证据写 `Perm.audit({action:'view', fields:['evidence']})`；
  学生端证据来自 `Perm.filterSnapshot`，越权由 `Perm.guardData` 拒绝。

## 政策沙盒 / 影子模式

把"风险规则三选一"升级成可试算的政策沙盒，让规则治理变成可视决策——教师不必"切了再看"。

**⚠️ 硬约束：试算只算不写。** 沙盒代码全部是纯计算 + DOM 渲染，绝不修改
`studentWarningStates` / `studentWarningHistory` / `warningSnapshots`，
也不调用 `saveStudentStates` / `addToHistory` / `writeWarningSnapshot`。
验收用"三个键的 JSON 字符串逐字节相等"来守住这条线（实测 39201B → 39201B，完全相同）。
只有点「应用此规则」才写 `riskPluginActive`——那只是切换当前生效规则，不回溯改历史。

- **入口**：「系统设置 → 政策沙盒（影子模式）」，选规则 + 覆盖阈值（不及格线 / 出勤率下限 /
  作业下限 / 实验下限，默认值取自三套插件源码里的真实参数）→「试算」/「A/B 版本对比」。
- **结果**：三档人数卡（规则 A vs 规则 B）、对比数字（新增预警 / 降级 / 等级加重 / 等级减轻 /
  不变，五类之和恒等于花名册人数）、ECharts 柱状图（复用本地 echarts，不引入新库）、
  名单差异表（仅 A 命中 / 仅 B 命中 / 两者都命中 / 全部，逐条列出姓名·学号·班级·原等级→新等级·分数变化）。
- **应用 / 取消**：应用前二次确认，提示"只影响之后的判定，历史预警不会被重新判定"；取消则丢弃试算结果。
- **健壮性**：花名册为空 → 提示"花名册为空，数据不足，无法试算"；50 人量级试算 **1 ms**（远低于 3 秒要求）。
- **插件层改动**：三套插件新增可选的阈值参数 `score(data, options)` / `detail(data, options)`，
  实现对 `failLine / attLine / hwLine / labLine` 的覆盖；**不传 options 时行为与之前完全一致**
  （`node test-risk.js` 6/6 全绿持续守住这一点）。加权版的等级由总分区间决定，
  阈值只影响因素标注——这在试算页有说明，不假装阈值能改变它的分数。
- **可验证性**：暴露只读诊断接口 `window.PolicySandbox`（`scoreAll/diff/defaults/peek`），
  便于自动化脚本独立核对"零副作用"与试算数字，**不提供任何写入能力**。

## 案例库反哺（给三 Agent 加记忆）

三 Agent 原本完全无状态：每次生成方案都从零开始，**历史上哪种方案真的有效，系统并不知道**。
本模块把已结案/已升级的工单沉淀成案例，在新预警生成帮扶方案时检索相似案例反哺 Agent2
——这是"系统会越用越准"的唯一证据。

```
工单状态 → 「已解除」/「已升级」
   ↓ 自动沉淀（去重键 = ticketId）
localStorage.caseBase（新的在前，最多 300 条）
   { id:'CASE-<时间戳36进制>', ticketId, studentId, className, riskLevel, riskScore,
     factors:[{dim,label,contribution}], planName, planSummary,
     checkinRate, outcome:'resolved'|'escalated', durationDays, closedAt }
   ↓ 新预警时检索
预警帮扶闭环流：… → 辅导员确认 → [case.retrieve 检索相似案例] → Agent2 帮扶规划师 → 生成工单 …
```

- **沉淀**：`changeStudentStatus` 变成 `resolved`/`escalated` 时触发；`factors` 优先取
  `warningSnapshots`，取不到就存空数组（不造数据）；`planName` 由方案文本**确定性关键词分类**
  （一对一辅导 / 错题专项 / 资料推送 / 学习计划调整 / 混合干预）。
- **相似度（零依赖、确定性、可解释）**：把 `factors` 归一化成各维度贡献占比，
  相似度 = 曼哈顿距离取反 ×0.85 + 风险等级相同加成 0.15，落回 `[0,1]`；
  同时给出可读理由（如"风险等级相同（高风险），且都以「成绩」为主要因素"）。
  检索为空或案例不足 3 条时如实说明（"案例库样本较少，仅供参考"），不虚构。
- **反哺 Agent2**：在 Agent2 之前插入 `case.retrieve` 工具节点，把检索结果注入其输入；
  上下文**脱敏**（只有班级与风险画像，绝不含姓名/学号），并保留"最终方案需辅导员审批确认"的约束。
  **不新增 AI 决策点**：Agent2 产出仍然只是建议，人工审批节点不变。
- **教师端展示**：「帮扶方案」页的「相似历史案例」（相似度 / 相似理由 / 当时方案 / 打卡完成度 /
  结果 / 耗时 + "本次方案参考了 N 条历史案例"）；「班级概览」的**「有效干预方式」**统计
  （按方案类型汇总解除率，样本数 < 3 标注"样本不足"）——直接回应"哪种干预真正有效"。
- **健壮性**：单条案例字段缺失就跳过该条；案例库为空时流程照常跑通，Agent2 退化为原始行为并标注
  "无历史案例可参考"。
- **可验证性**：只读诊断接口 `window.CaseRefeed`（`lastRetrieval / lastAgent2Input / findSimilar /
  effectiveness`），用于核查"注入 Agent2 的上下文已脱敏"。
- **后续演进**：当前是纯前端确定性检索；案例量级上来后可将 `findSimilar` 换成 sqlite-vec
  （或其它本地向量检索）以获得语义相似度，接口保持不变。当前**刻意不引入** embedding 服务。

## 正向预警 / 育优预警

系统不再只会说"你有危险"。新增一套**正向评分**（[riskPlugins/positiveRule.js](学情预警/riskPlugins/positiveRule.js)），
用同一批字段回答"你在这方面很强"——叙事从"盯差生"变成"学生发展平台"，边际成本极低。

**两套评分彼此独立**：正向规则**不注册进** `RiskPluginManager.plugins`（那会污染风险评分），
不读也不写风险状态，纯函数式实时计算，**不新增 localStorage 键**，全部规则化、不调用模型。

| 维度 | 权重 | 取数 |
|---|---|---|
| 学业表现 | 0.40 | 课程加权均分（高数/编程 1.2，英语/计算机基础 1.0，与加权版的权重思路一致） |
| 行为自律 | 0.25 | 出勤率、作业提交率 |
| 学习韧性 | 0.20 | `MM.wrongBook` 的复习次数与掌握比例 |
| 进步幅度 | 0.15 | 与 `studentWarningHistory` 历史分数的提升（不足两条记录则不计） |

输出 `{ score, level:'A'|'B'|'C', strengths:[{dim,label,score,reason}], suggestions }`；
某维度数据缺失时按剩余权重归一化，**不猜数据**；`score ≥ 85` 为 A、`≥ 70` 为 B；
`strengths` 只收录 ≥70 的维度并给出**具体数据支撑的理由**，例如
"出勤率 100%、作业提交率 100%，全勤且作业零缺交，自律性突出"。

- **学生端「我的优势」**：优势标签（取分数最高的 2 项，--color-success 系）+ 一句话理由 +
  规则映射的建议（学业表现 A → 竞赛/科研；学习韧性 A → 带同学复习；进步幅度 A → 进步奖学金），
  每条建议都带"具体以学校政策为准"，不给绝对承诺。
  **若同时有风险预警，先显示预警解释卡、再显示优势卡片**——风险信息是学生必须知情的，
  优势信息是激励性的；这个顺序与正向措辞都是刻意的，避免"被系统盯上"的挫败感。
- **教师端「可重点培养名单」**：学生/班级/优势得分/优势等级/优势标签/**风险等级**，
  可按优势得分升降序，可导出「育优名单」（复用 `downloadXLSX`，内容与页面顺序一致）。
  同时显示风险等级是这份名单真正的价值点——**"高风险但某维度有潜力"的学生最容易在帮扶中被忽略**。
- **文案红线**：正向评分不作为任何奖励的自动依据（UI 标注"仅供辅导员参考"）；
  不展示学生之间的排名；涉及奖学金/保研一律加"以学校政策为准"；导出文件里也带这条说明。

## 多源画像 · 个性化证据融合（MVP-1 算法骨架）

单靠成绩做画像有先天缺陷：**滞后**（一学期 3~4 次月考）、**稀疏**、**单一**（看不到行为变化）。
本项目补上校园多源行为信号（考勤、作业、一卡通消费、门禁外出），并用一个可解释、可复现的
融合算法把"期末算总账"变成"期中就发现"。

### 算法五步（`profileFusion.js`，纯函数、零依赖、ES5）

| 步骤 | 做法 | 为什么这么做 |
|---|---|---|
| 1 个体基线（**多参考**） | 并行跑两套参考假设：**锚定参考**（学期初固定窗）与**滑动参考**（长窗 42 天且排除最近 7 天 vs 短窗 7 天），各自鲁棒标准化后取证据最大者 | 两套参考的失效模式是**互补**的：锚定参考怕早期恶化污染，滑动参考怕"适应掩盖"（持续恶化会被自己追平）。取最大相当于两种变化假设的并集，在固定误报预算下白拿一次灵敏度 |
| 2 时间衰减 | `exp(−Δt/τ)`，τ：成绩 45 天、考勤/作业 12 天、消费/门禁 4 天 | 行为必须新鲜，成绩证据可留存；同时解决异步、不等间隔采样 |
| 3 对数几率融合 | `d(t) = Σ wₛ·zₛ(t)·decayₛ(t)`，两组权重画像：`raw`（原始次数）/ `features`（节律特征） | 异质源统一量纲；权重可解释，MVP-2 可用标签学习 |
| 4 自中心化 | 减去该生参考窗内自身的平均偏离 | 成绩源在参考窗内无观测、只能用群体基线，会让半数学员带**恒定正偏置**；不做这一步累积通道会把常量一路积分 |
| 5 双通道 | 急性 `A(t)=Dc(t)/σ` + 累积 `B(t)=max(0,B(t−1)+A(t)−0.5)`，取 `max(A,B)` | 急性通道抓突变（更早），累积通道抓慢性恶化（抗噪）。实测急性通道在提前量与 AUC 上都最优，故设为默认 |

**冲突度** `K(t) = 1 − |Σw·z| / Σw·|z|`：各源打架时（成绩好但行为异常）K 升高，这类样本应
**转人工核实**而不是自动升级等级——"不确定时找人，而不是不确定时下结论"。

### 仿真验证与结论（`npm run test:fusion`）

真实校园数据拿不到，因此用**可控仿真**（`signals.js`）：有 latent 风险真值、各源独立发射模型、
个体基线差异，以及混杂项（**兼职生**外出多但无风险、**困难生**消费低但无风险）。
仿真里知道真值，才能算提前量、AUC 与消融增益。参数在建模时固定、不按结果回调；
开发用 seed 1..3，**结论报告在留出的 seed 101..105 上**（200 人 × 112 天）。

**操作点 A：目标误报预算为 10%，采用按学生确定性二折双向交叉标定**：一半学生只用于选阈值，另一半只用于评估，再交换汇总，避免在评估样本上调阈值。

| 检测器 | 误报率 | 检出率 | 平均提前(天) | 期中 AUC |
|---|---|---|---|---|
| ① 仅成绩（单源现状，月考节奏） | 9.1% | 81.2% | **−12.2** | 0.793 |
| ② 现行系统（成绩+考勤+作业，绝对阈值） | 8.7% | 98.8% | **+4.2** | 0.829 |
| ③ 融合 · 原始次数（MVP-1） | 10.6% | 86.9% | **+10.1** | 0.904 |
| ④ 融合 · 节律特征 · 个体基线（MVP-2a/b） | 9.9% | 86.1% | **+12.9** | **0.907** |
| **⑤ 并集 · 阈值 OR 融合（MVP-2c）** | **5.9%** | **96.8%** | **+5.4** | **0.901** |

**操作点 B：把检出率对齐到 95%**，看各方要付多少误报、能提前多久：

| 检测器 | 平均提前(天) | 误报率 |
|---|---|---|
| ① 仅成绩 | +3.3 | 25.1% |
| ② 现行系统 | **−2.9** | **4.0%** |
| ④ 融合 | **+22.1** | 17.3% |

### 计数型信号的三种尺度（MVP-2e）

计数型信号（外出次数/消费额等）是非负量，尺度选择直接决定公平性：

| 配置 | ④ 提前 | ④ 检出 | ④ AUC | ⑤ 提前 | ⑤ 检出 | ⑤ 误报 | 个体基线偏差 | 群体阈值偏差 |
|---|---|---|---|---|---|---|---|---|
| **泊松方差归一化（默认）** | 11.5 | 86.3% | **0.905** | 7.1 | 97.3% | **6.4%** | **3.0%** | 13.5% |
| log + 固定下限 | **13.7** | **88.7%** | 0.901 | **9.1** | **97.7%** | 7.1% | 7.0% | 13.5% |
| 线性尺度 | 9.0 | 84.8% | 0.906 | 7.5 | 97.3% | 6.7% | 3.6% | 16.2% |

**做法**：取对数后按泊松用 delta 方法给噪声标准差 —— `sd(log(1+X)) ≈ √(φλ)/(1+λ)`，λ 是该生**自己的基线水平**（φ=2 为过散系数）。
λ 小（"宅"）则噪声大，偶发 0 次不会被当成异常；λ 大则噪声小，相对下滑更容易被判异常。
于是同时保住了 log 的"相对变化可比"与按各自噪声定显著性的公平性：
**个体基线偏差从固定下限的 7.0% 压到 3.0%（比线性尺度的 3.6% 还低），误报也从 7.1% 降到 6.4%**，
只让出约 2 天提前量。三种配置的公平性都远好于群体阈值（13.5%~16.2%）。

### 最终算法架构：两种用途，两套检测器

| 用途 | 用哪个 | 理由 |
|---|---|---|
| **报警**（宁可多报也不漏） | **⑤ 阈值 OR 融合** | 四个指标全面不劣于现行系统：提前 **+3.1 天**（3.9→7.1）、误报 **6.4% vs 8.1%**、AUC **0.901 vs 0.829**、检出 97.3% vs 98.8%（基本持平） |
| **排序 / 分流**（把有限的辅导员精力排优先级） | **④ 纯个体基线融合** | 提前量最大（**+11.5 天**），但检出只有 86.3%——适合"谁最该先看"，不适合"谁必须报" |

**⑤ 的实现要点（FAR 预算拆分）**：把误报预算一分为二，融合与绝对阈值各按 FAR/2 标定，
任一报警即报警——等价于分数空间比较 `max(融合/τf, 阈值/τr) > 1`。
**不能**把两条通道的原始分数直接取 max：那是"噪声或"，排序会被尾部最重的通道主导
（实测 AUC 从 0.906 掉到 0.821）。

**结论**：

1. **多源补齐对"只看成绩"最有效**：④ 比 ① 平均提前 **约 20 天**、AUC **+0.113**。
   单靠月考成绩会把预警拖到临界日之后才发现——"单源画像"的硬伤被量化了。
2. **多时间尺度 + 多参考基线（MVP-2b）达成了"更早"**：④ 在同等误报下领先现行系统 5 天。
3. **把绝对阈值通道并进并集（MVP-2c）补回了"更全"**：⑤ 用预算拆分把两者的优势合起来，
   在**同一误报预算**下四项指标全面不劣于现行系统。这是本项目的最终算法结论。

### 一个被证伪的改进：多尺度滑动参考（MVP-2f）

设想很自然：滑动参考只有一个尺度（42 天长窗 vs 7 天短窗），长窗滞后太大，那就再加一个
**21 天中窗**并行（“长/中/短”三窗），理论上能更早抓住"两三周前开始的持续变化"。

**实测：零影响。** 四项指标（④提前/④检出/④AUC、⑤提前/⑤误报）与双窗版**完全一致**。

诊断（`test-fusion.js` 里可复现）：

| 检验 | 结果 |
|---|---|
| 通道归属（谁提供最大证据） | 锚定 40.6% · 长窗 21.0% · **中窗 38.5%** |
| 事件学生中 | 锚定 81.2% · 长窗 5.0% · 中窗 13.9% |
| **逐人比较"首次报警日"** | **相同 200 人 / 不同 0 人** |

**解释**：中窗确实提供了大量“更强证据”，但**锚定参考（学期初、不复位）对同一次恶化总是更早越线**，
中窗的额外证据全部落在报警之后；它也没有抬高任何非事件学生的最大分，所以误报阈值不变。
**结论**：默认**关闭**中窗（保留 `midWindow: true` 开关，供真实数据复测）。

> 这类"看起来一定有用、实测完全无用"的改动，如果只报增益不报证伪，就是在自欺。
> 所以它和诊断代码都留在验收脚本里。

### 权重学习：换了目标函数之后，根因终于被定位（MVP-2d / 2g）

权重一开始是**专家先验**。也实现了用标签把它学出来的通路：
`learnFromCohorts()` → 逐源标准化特征 + **L2 正则向先验收缩**；标签在产品侧来自
`warningAppeals`（采纳=负样本、驳回=正样本）与 `caseBase`（escalated=正样本）。

第一版用**逻辑回归拟合"第 56 天是不是事件学生"**这个二分类标签，实测学不过先验。
怀疑是**目标错配**（检测器评价的是"多早报警 + AUC 排序"，不是分类），于是实现了
**RankNet 风格的成对排序损失**：

```
L = Σ_(i∈正, j∈负) log(1 + exp(−(s_i − s_j))) + λ‖w − w_prior‖²
```
（AUC 的可微替代；正负对为 O(n²)，故每轮用确定性 PRNG 抽样 `pairsPerIter` 对。）

**结果：排序目标确实比二分类略好，但两者都没有赢过任何先验。** 于是回头做了一个
更根本的对照——**无信息先验（各源等权，不看任何实验结果）**：

| 基准 | ④ 提前(天) | ④ AUC | ④ 检出 |
|---|---|---|---|
| 调优后的专家先验 | 11.5 | 0.905 | 86.3% |
| **无信息先验（等权）** | **10.6** | **0.904** | **88.5%** |

**两者几乎相同 ⇒ 权重本身对性能影响很小。** 这就解释了全部现象：

| 目标函数 | 检查点 | ④ 提前(天) | ④ AUC | 相对等权先验 |
|---|---|---|---|---|
| 二分类 | 第 35 天 | 8.7 | 0.892 | ❌ 没更好 |
| 二分类 | 第 56 天 | 9.6 | 0.882 | ❌ 没更好 |
| 排序 | 第 35 天 | 9.3 | 0.892 | ❌ 没更好 |
| 排序 | 第 56 天 | 9.9 | 0.881 | ❌ 没更好 |

**根因**：6 个源只是同一个 latent 风险的**不同噪声投影**，信息高度冗余；性能来自
**多参考 / 多通道 / 方差归一化**这些结构设计，而不是权重分配。只有各源携带**互补**信息时，
权重学习才可能有收益——这同时解释了为什么此前"调参"也调不出差别。

**产品含义**：权重学习**默认不启用**，必须通过 `shouldAdopt()` 这道 **champion/challenger 闸门**
（留出集上提前量 +0.5 天以上、AUC 不倒退 0.005 以上、误报不显著变差）；本次 0/4 通过。
**不悄悄换模型**，也不为了"看起来做了学习"而把没增益的权重上线。

### 公平性：个体基线最扎实的收益

同一"外出次数"信号、同等误报预算下比较两组学生的误报率偏差（disparity）：

| 规则 | 总体误报 | "宅"的学生 | "爱出门"的学生 | 两组偏差 |
|---|---|---|---|---|
| 群体阈值（低于全校中位数） | 7.9% | 16.2% | 0.0% | **16.2%** |
| 个体基线（低于自己的学期初水平） | 9.9% | 8.1% | 11.7% | **3.6%** |

群体阈值对"宅"的学生**系统性误报**（16.2% vs 0.0%）；个体基线把它压到 3.6%。

### 已知问题（待改进，已写进验收输出）

1. **计数型信号的尺度**：外出次数/消费额是非负量，低基线学生的向下偏离被 0 截断（下限效应）。
   本版用"群体尺度下限兜底"把偏差从 16.2% 压到 3.6%；进一步应改用对数尺度或泊松/负二项残差。
2. **参考窗与恶化起点的耦合**：MVP-2b 已用"锚定 + 滑动"双参考缓解；
   更彻底的做法是给滑动参考也加多尺度（长/中/短三窗）。
3. 行为信号为**自建仿真**，属方法验证，**不是真实校园数据上的效果承诺**；
   接真实数据前必须重新标定，且行踪轨迹属 PIPL 敏感个人信息，需取得**单独同意**。

- `campusProfile.js` / `demoSeed.js`：把算法接到业务上（单独同意、撤回、名单、解释、审计），

### 落地：单独同意 → 进入名单 → 可撤回（MVP-3）

算法之上加了一层产品适配（`campusProfile.js`），把**合规做进流程**而不是写在文案里：

```
教师端「班级概览 → 重点关注名单（多源行为画像）」
   ├─ 「载入演示行为数据」  → 写入 localStorage.campusSignals（真实场景由校方数据接口写入）
   ├─ 未授权时名单为空，并显示"已排除 N 名未授权学生"
   └─ 已授权学生按关注度排序：学生/班级/关注度/主要贡献来源/证据冲突/查看画像
        （查看即写审计 Perm.audit({action:'view', fields:['campusSignals','fusionScore']})）
学生端「隐私中心 → 校园行为数据」
   ├─ 单独同意开关（默认未授权），写明范围与目的、可追溯
   ├─ 授权后可自查"我的行为画像"（关注度 + 各源偏离度与贡献）
   └─ 撤回后：立即不再参与画像、从教师端名单消失，撤回动作写 authLog 留痕
```

关键设计点：

- **默认未授权**：不授权就不进名单、不参与任何打分——不是"默认开启、事后关闭"。
- **口径一致**：教师端名单与学生自查用**同一个池子**（都只含已授权学生）计算，
  验收里 12 名学生逐一比对，得分不一致 0 人。代价是关注度天然是**相对值**，
  这点在两端 UI 都明确标注，并提示"不是风险等级"。
- **存入的数据不含 latent 真值**：`Signals.toStore()` 会剥掉仿真真值——系统不该看到"答案"。
- **证据冲突**：各源互相矛盾（如成绩好但作息异常）时冲突度高，UI 提示"建议先人工核实"，
  这是"不确定时找人"而不是"不确定时下结论"。
- **教师端另有「演示：批量授权」**按钮（带二次确认与明确说明），只为让演示不卡在授权环节；
  生产环境必须逐人授权，这一点写在按钮的确认文案里。

**验收（32 项，全部通过）**：覆盖未授权为空/已排除计数、单独同意写入范围与目的、
授权后进入名单、查看写审计、撤回后即时消失、撤回留痕、两端口径一致、无 JS 异常等。

## 多模态能力

所有多模态入口都在两个页面顶部的「AI 多模态」折叠栏里，统一由 `multimodal.js` 调度。

### 1. OCR 图文识别 — 级联架构

```
图片 → ①本地 Tesseract(chi_sim+eng，离线免费)
        ↓ 结果为空 / 置信度 < 55 / 字符数 < 4
      ②多模态大模型 qwen-vl-plus（联网，识别手写+公式更准）
        ↓ 全部失败
      ③Mock 兜底（保证演示不中断）
```

- 图片自动压缩到最长边 1280px；识别结果标注实际使用的引擎与置信度。
- 教师端入口：表单区「📷 拍照识别」与模态栏「拍照 / 上传识别」，结果可直接填入「学业成绩」。
- `CONFIG.multimodal.ocrEngine`：`auto`（默认，级联）/ `tesseract`（纯离线）/ `vlm`（纯大模型）/ `mock`。

### 2. ASR 语音转文字 — 双通道

| 通道 | 入口 | 说明 |
|---|---|---|
| 实时听写 | 「实时听写」按钮 | Web Speech API，麦克风实时转写，再次点击停止 |
| 音频文件 | 「音频文件」按钮 | 上传 wav/mp3/m4a/webm，走大模型 ASR（`qwen3-asr-flash`） |

主进程已注册麦克风权限处理器（`media` / `audioCapture`）；环境不支持时给出提示并回落模拟结果。

### 3. 错题拍照答疑 + 错题本

```
拍照 → OCR 识别题目 → 知识库 RAG 关联知识点 → 多模态大模型解题 → 存入错题本
```

输出结构固定为：题目识别 / 解题思路 / 完整解答 / 易错点 / 同类练习。学生端「错题本」标签页支持复习打卡、标记掌握、删除。

### 4. 知识库文档上传 — 真实解析

支持 `.txt / .md / .csv / .json / .xlsx / .xls`：读取 → 分块（600 字 / 80 字重叠）→ 生成知识点 → 写入知识库并持久化。`.pdf / .docx / .pptx` 会明确提示先转文本。

### 5. 降级策略

`CONFIG.multimodal.enableMockFallback = true` 时，任何真实能力失败都会回落 Mock 并在 UI 上标注「已降级」，保证演示不因网络问题中断。

### 6. 本地 OCR 为什么跑在独立进程里

`tesseract.js` 初始化 worker 时会**同步阻塞所在进程的事件循环**（实测 20–30 秒以上）。
它最初跑在主进程里，后果是：窗口无响应、IPC 与 DevTools 端点全部超时，甚至连 `setTimeout`
都不会触发（时间片被占满）——也就是说加超时和熔断都救不了。

现在本地 OCR 由 `ocrProcess.js` 在 Electron `utilityProcess` 中执行，主进程只做转发与超时保护：

```
渲染进程 ──IPC──▶ 主进程（只转发，永不阻塞）──message──▶ utilityProcess: ocrProcess.js
                                                              └─ tesseract worker（卡也只卡它自己）
```

- 主进程侧 45 秒无响应 → 杀掉子进程并返回失败，前端级联到大模型 / Mock。
- 渲染侧另有 15 秒超时（`multimodal.js` 的 `localOcr`），保证「识别中…」不会无限挂住。
- 连续失败 2 次（或初始化阶段失败）→ 本次会话熔断本地 OCR，直接降级。

实测：断网时首次 OCR **约 0.9 秒**返回 Mock，期间窗口心跳保持 2–4ms（修复前是 15–30 秒完全冻结）。

## 错题回流预警

把学生端的错题本变成预警系统的**数据源**：

```
学生拍照上传错题 → 存入错题本（按知识点打标）
        ↓ 同一知识点「未掌握 + 复习中」≥ 3 题
      生成预警候选（写入 localStorage: warningCandidates）
        ↓ 教师端看板「错题回流预警」实时展示
      辅导员点「生成预警工单」→ 学生风险等级上调 + 操作日志留痕
        ↓ / 或点「忽略」
```

- 阈值：3 题升「中风险」候选，5 题升「高风险」候选（`MM.warning.thresholds`）。
- 教师端位置：班级概览看板最下方「错题回流预警」表格。
- 学生端位置：错题本页顶部「薄弱知识点」区块，显示每个知识点的未掌握/总数。
- 数据跨页面共享（同一 Electron 会话的 `localStorage`），支持 `storage` 事件自动刷新。

## 任务流引擎

`flowEngine.js` 是一个零依赖的轻量任务流引擎，把原来写死在业务代码里的多步 AI 流程抽成 JSON DSL。

### 节点类型

| 类型 | 说明 |
|---|---|
| `trigger` | 触发节点（流程起点） |
| `tool` | 确定性工具：OCR、知识库检索、写库、生成工单…… |
| `llm` | 大模型节点 |
| `agent` | **Agent 节点（三 Agent 契约层）**：输出必须通过 JSON Schema + 语义校验才允许推进 |
| `human` | 人工节点（确认 / 审批，可挂起） |
| `condition` | 条件分支（`then` / `else` 跳转） |
| `notify` | 通知节点 |
| `end` | 结束节点 |

步骤通用字段：`id` / `type` / `label` / `input`（支持 `${path}` 取值）/ `output` / `next` / `then` / `else` / `reject`。

`agent` 节点校验失败时不会让流程崩掉，也不会带着脏数据往下走：该步骤记为 `blocked`，流程跳到 `reject` 分支（转人工兜底），运行状态为 `blocked`。

### 内置任务流（flows.js）

| 流程 | 说明 |
|---|---|
| 📷 拍照错题闭环流 | 拍照 → OCR → 知识库匹配 → 大模型解题 → 确认入库 → 薄弱点回流预警 |
| 🗂 多模态学业数据录入流 | 教师上传成绩单 → OCR（低置信度升级大模型）→ 结构化抽取 → 人工确认 → 填入表单 |
| ⚠ 预警帮扶闭环流 | 读画像 + 跑规则 → Agent1 → 辅导员确认 → 检索相似案例 → Agent2 → 生成工单（带 actions 与完成标准） |
| 🔎 帮扶执行复核流 | 汇总执行证据 → Agent3 逐项核查 → 按结论分流（不达标提示人工复核，达标由辅导员决定结案） |

### 特性

- **可回放**：每次运行产生时间线（节点 / 状态 / 耗时 / 输出 / 错误），持久化到 `localStorage: flowRuns`（保留 50 条）。
- **条件分支**：内置极简条件求值（`${ocr.confidence} < 55`），**不使用 eval**。
- **人工节点**：拒绝时可跳转 `reject` 分支。
- **失败可降级**：单个节点失败会记录错误并终止该次运行，不影响系统。
- 入口：教师端顶部导航「任务流」，可「运行」或「查看定义」。

## 三 Agent 契约层（agents.js / agentBridge.js）

`docs/三Agent协同专属提示词.md` 定义了三类专职 Agent 的提示词与 JSON 契约。本轮把这套规范从"文档"落成"代码"：

| 文件 | 职责 |
|---|---|
| `agents.js` | 契约层：提示词（与文档逐字对齐）、输入模板构造、JSON Schema + 语义校验、降级模板、调用留痕 |
| `agentBridge.js` | 数据桥：把平台数据（画像 / 规则引擎 / 案例库 / 工单 / 操作日志）映射成契约输入，把结构化输出渲染成可读卡片 |

### 为什么需要这一层

改造前三 Agent 是三个 `tool` 节点 + 自由文本输出：提示词散在 `app.js` 的默认配置里与文档不一致、模型返回什么都直接当结论、每次调用的输入输出不留痕。现在：

1. **提示词只有一份真相**：改文档 → 改 `agents.js`（`SYSTEM_PROMPTS` / `COMMON_CONSTRAINTS`）；教师端「AI Agent 配置」弹窗直接读它，老师自己改过的提示词会被保留并标注「已自定义」。
2. **输出必须先过校验**：`Agents.validate()` 检查枚举、必填、风险分是否被改写（`RISK_SCORE_CHANGED`）、结论引用的 `evidence_id` 是否真实存在（`UNKNOWN_EVIDENCE_ID`）、完成标准是否可核实（`NON_MEASURABLE_CRITERIA`）、"没有数据"是否被误判成"未完成"（`NO_DATA_BUT_JUDGED` / `STALE_OBSERVATION`）等；不过则重试一次，仍不过就 `blocked` 转人工。
3. **每次调用都留痕**：`localStorage: agentCalls`（保留 200 条，新的在前）记录 `caseId / agentId / version(提示词版本) / model / input / output / evidenceRefs / validation / attempts / durationMs / calledAt`，可用 `Agents.calls({caseId})` 检索。
4. **离线可演示**：未配置模型密钥、或调用失败时，`Agents.mock()` 生成**同样通过校验**的降级输出（明确标注"降级模板"），流程与校验路径完全一致，不会因为断网白屏。

### 与规则引擎的边界

风险等级与分数由确定性规则引擎给出（`RiskPluginManager`），`agentBridge.ruleResultFor()` 现场跑一次当前生效的规则并把它作为 `rule_result` 传给 Agent1；Agent 只解释、不改分（改了会被 `RISK_SCORE_CHANGED` 拒绝）。Agent3 仅在执行期结束 / 约定复核日 / 人工发起时运行（独立流程 `flow-review`），不会紧接 Agent2 立即跑。

### 自检

```bash
node test-agents.js     # 契约层独立验证套件（提示词逐字比对 / 正反例校验 / 留痕 / 流程联调）
node test-flow.js       # 流程引擎护栏回归
```

## 配置说明

三 Agent 支持独立配置 OpenAI 兼容的聊天接口。使用源码运行时，将 `config.example.js` 复制为 `config.local.js`，把变量名改为 `CONFIG_LOCAL`，然后仅填写自己的密钥：

```js
var CONFIG_LOCAL = {
  agentApi: {
    chatUrl: 'https://api.deepseek.com/chat/completions',
    model: 'deepseek-flash',
    apiKey: 'YOUR_DEEPSEEK_API_KEY'
  }
};
```

保存后重启应用。未配置或调用失败时，平台会按 Agent 规则降级并标记；三 Agent 的输出还须通过 JSON 结构和证据校验。`config.local.js` 已加入 `.gitignore`，也从 Windows 安装包中排除。发布安装包不会携带个人 API 凭据；安装版默认使用安全占位配置。

Windows 安装包由 `npm run build:win` 生成在 `dist/`。从源码运行和开发请使用 `npm install` 后 `npm start`。

- `nodeIntegration: false`、`contextIsolation: true`
